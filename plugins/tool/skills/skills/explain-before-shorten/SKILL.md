# Explain Before Shorten

「短く書く」より先に、「相手に口頭でどう説明するか」を考える。
言葉だけを削るのではなく、その説明で扱う話題を絞って簡潔にする。

## 前提と担当範囲

- 対象の文章と、理解に必要な前後の文脈を読む。図表が説明の一部なら、その内容も確認する。
- 読み手、目的、文体、長さの指定を優先する。会話ですでに分かっていることは聞き直さない。
- 必須のツール、MCP サーバー、認証はない。ファイルの編集や事実確認には、その作業に適したツールを使う。
- 「口頭で説明する」は内容を整理する方法であり、完成文をくだけた口調にする指示ではない。
- 専門用語の禁止や、すべての文への主語の追加は行わない。文脈で明らかなものは省略できる。
- レビューや相談は提案まで。「直して」など編集を依頼されたら、指定された範囲の正本へ反映する。
- 文章の自然さを整えるために、無関係なページや既存のスキルを変更しない。

## 手順

1. **この説明で何を伝えたいかを決める。**
   読み手に理解してほしいことを、一文で整理する。
   仕組みを知る、違いを理解する、手順を実行するなど、文章の役割に合わせる。
   概念説明にも採用判断や行動指示を無理に加えない。
   原文から目的を読み取れなければ、推測を確定事項にせず、前後を確認する。

2. **まず、口頭ならどう説明するかを考える。**
   文字数を気にせず、読み手が隣にいるつもりで説明を組み立てる。
   「何がどうなるか」「なぜそうなるか」「どんな場合か」を、必要な範囲で具体的にする。
   「分離」「管理」「対応」「保証」などの語だけで、実際の動きや条件を代用しない。
   事実、推奨、可能性を区別し、原文にない動作や効果を作らない。

3. **違う話を分け、その場所で必要なものを選ぶ。**
   仕組み、利用条件、例外、注意点を区別する。
   実行時間の制限、必要な設定、通信の待ち時間など、異なる話を一文につなげない。
   条件は対応する表のセルや文の近くへ置くなど、どの説明にかかるかを明確にする。
   重複する補足や主題から外れる話は省略・移動を検討する。
   ただし、適用条件や重要な制約を、文字数のために消したりノートだけに隠したりしない。
   大きな削除・移動やページ構成の変更が必要なら、依頼範囲を確認する。

4. **意味を保って短くする。**
   重複、不要な前置き、回りくどい修飾を削る。
   主体、動作、因果関係、比較対象、重要な条件を読み取れる状態に保つ。
   「上限数は到達保証ではない」のような、短いだけの独自表現を作らない。
   公式用語は維持し、初出で必要な意味を補足する。
   言葉を削るだけでは収まらない場合は、扱う話題を減らすか構成を見直す。
   文字を小さくしたり略語を増やしたりして、読み手に解読を押し付けない。

5. **短くした文章だけで伝わるかを確かめる。**
   元の長い説明や口頭補足を知らなくても、何の話で何が起きるかが分かるか確認する。
   隣り合う文を続けて読んで、話題が突然変わらないか、用語の意味が揺れていないか確認する。
   不自然さが残る場合は、単語の置換を繰り返すのではなく、説明の組み立てに戻る。
   短くしたことで意味が失われたら、必要な言葉を戻す。

6. **編集した場合は、保存結果と表示を確認する。**
   ユーザーの既存の変更を保持し、本文・表・図・注記の意味を揃える。
   固定サイズのスライドでは、対応するツールで改行やフッターとの重なりも確認する。
   自動診断が正常でも、表示上の重なりがないとは限らない。必要なページを実際に見る。
   未確認の内容や保存できなかった箇所は、確認・反映済みと報告しない。

## 書き換えの例

| 短くしすぎた表現 | 口頭でも説明しやすい文章 |
| --- | --- |
| 受付と完了確認を分離する | 処理の終了を待たずに受付済みと返し、結果は後から問い合わせる |
| 上限数は到達保証ではない | クォータなどの制約により、表の台数まで増やせない場合がある |
| 上限なしでも中断に備える | 実行時間を無制限にしても、サービス側の更新などで処理が止まることがある |

例文は表現の作り方を示すもので、別の製品や構成にそのまま当てはめない。
読み手が必要とする技術用語は、別の曖昧な言葉に置き換えない。

## 出力

- 通常は完成した文章を先に示し、意味や構成を変えた点だけを短く説明する。
- 編集依頼では正本へ反映し、主な変更を簡潔に報告する。提案を繰り返して承認を取り直さない。
- 相談やレビューでは、必要なら「伝えたいこと」と書き換え案を示す。未反映なら明記する。
- 口頭説明用の下書きや検討過程は、通常の出力に毎回並べない。

## 不足情報への対応

| 状況 | 対応 |
| --- | --- |
| 原文の意味が複数に取れる | 前後を読み、それでも決まらない場合だけ質問する |
| 技術的な条件を確認できない | 不確かな点を明示し、推測で断定や保証を加えない |
| 指定の長さでは条件を保てない | 無理に圧縮せず、必要な長さや構成変更を提示する |
| 表示や保存を確認できない | 文章の改善と、確認できていない範囲を分けて報告する |

## Post-Run Reflection

最後に、伝えたいことが完成文から読み取れるか、短くするために条件を落としていないか、
違う話を詰め込んでいないか、公式用語と自然な日本語を両立できているかを黙って確認する。
提案と編集の範囲を守り、保存・表示を確認していないのに完了扱いしていないかも確認する。
ユーザーからの修正は同じ会話で生かすが、依頼なしにスキルや設定へ書き戻さない。
